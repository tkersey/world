# Boundary World Contract

This document describes the v0 contract between Boundary Certified Targets and World.

## Expected Target Fields

World expects a Boundary target to expose these public fields:

- `Program`: residual `Program.Session` execution machine.
- `WorldSurface`: target-neutral surface metadata with `surface_fingerprint`.
- `WorldPortTable`: dense world-port entries scoped to one surface fingerprint.
- `WorldValueTable`: payload/resume/result value references for each port.
- `WorldDispatchTable`: residual site index to dense `world_port_id` mapping.
- `SourceMap`, `TraceMap`, `EvidenceMap`: audit metadata when available.
- `NormalForm`: Boundary Normal Form.
- `Certificate`: target certificate with `certificate_fingerprint`.
- `replay_key_recipe`: Boundary replay-key metadata when available.

World uses these public target APIs and does not inspect Boundary internal mutable state.

## Fingerprint Validation

Dense `world_port_id` values are only stable inside one `WorldSurface.surface_fingerprint`. A World run validates the expected surface fingerprint before trusting the dispatch table when the caller supplies `expected_world_surface_fingerprint`.

The target certificate fingerprint is likewise validated when the caller supplies `expected_target_certificate_fingerprint`.

## Dense Port Scope

`WorldPortTable.entries[index].world_port_id` must equal `index`. `Machine` construction calls Boundary target assertions that prove the dense surface and dispatch profile. A descriptor generated by `world.port(Target, Site, handler)` must match both residual site index and residual site fingerprint.

## Dispatch Table Usage

The hot path is:

1. `session.next()`
2. read the residual operation site index and fingerprint
3. `Target.WorldDispatchTable.lookup(site_index)`
4. validate the dispatch entry fingerprint
5. index the handler table by dense `world_port_id`
6. resume the typed Boundary session request

World dispatch does not match operation names on the hot path.

## Value Table Usage

Boundary provides `WorldValueTable` entries for payload, resume, and result refs. World descriptors expose the corresponding payload and response types from the residual site descriptor and preserve source/world-port refs on `PortRequest`.

## Handler Response Ownership

The default `world.port` ABI treats handler responses as borrowed. World clones the response into retained run storage and transcript storage before resuming Boundary; it does not assume ownership of the handler's source allocation.

Handlers that return an owned response allocation must use `world.portWithOptions` with `response_deinit`. World calls that cleanup hook after cloning the response in fresh and verify modes, keeping replay mode owned by transcript/run storage only.

## Replay Keys

The v0 replay key is deterministic and includes:

- `WorldSurface.replayScopeRef().fingerprint`
- dense `world_port_id`
- request fingerprint
- response fingerprint

Replay mode fails if a matching response is missing, if the surface changes, if the target certificate changes, if the port id changes, if the request fingerprint changes, if the response kind changes, or if response events remain unused at run completion.

## Hot-Path Invariants

World v0 must not perform treaty resolution, provider harness execution, provider catalog lookup, morphism catalog lookup, closure graph traversal, evidence graph traversal, Boundary normalization, or operation-name string matching during dispatch.

Boundary is responsible for eliminating supported internal Boundary-native routes before World runs the target. World interprets only explicit residual WorldPorts.

## Future World-WASM Direction

The v0 Zig handler ABI is intentionally local. The `Machine.start` and `Run.next` step API preserves the control shape needed for future variants such as WASM, externally scheduled, UI-driven, human-approval-driven, or persisted execution, without implementing those systems in v0.
